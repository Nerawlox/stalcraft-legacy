# Учёт последствий общественного офлайн-патча

Дата: 4 октября 2026. Это первый статический реестр для планирования законченной играбельной версии и передачи проекта сообществу. Игру для этого аудита не запускали и игровые исправления не добавляли.

Сравниваются **файлы полученного пакета**, а не доказанно нетронутая официальная версия. Его `classes.jar` уже содержит отсутствующие серверные методы и пустые callbacks. Поэтому «этого нет в нашей базе» и «это удалил офлайн-патч» — разные выводы. Год и авторство пакета этим сравнением не устанавливаются.

## Что проверено

Проверены все 197 `.class` записей `offline-patches.jar`, базовые архивы в порядке `classes.jar → libs.jar`, внутренние имена классов и изменённые методы. Результат:

| Категория | Количество | Значение |
| --- | ---: | --- |
| Подменённые классы | 35 | Отличаются от класса по тому же пути в базе; изменения методов перечислены в реестре. |
| Новые вспомогательные классы | 2 | `ServerPacketHandler` и `local.stalcraft.OfflineHook`. |
| Неизменённые классы по тому же пути | 3 | `GloomyHooks`, `ifxb`, `stalker.misc.qlfw`: полное совпадение байтов. |
| Дубли CarpentersBlocks под другим путём | 144 | Непустые классы полностью совпадают с каноническими копиями в `classes.jar`. |
| Пустые записи | 13 | Все в семье CarpentersBlocks; пустые канонические копии также есть в базе. Это не восстановленный код. |

Таким образом, патч не содержит 184 независимых переписываний механик. Значительная часть архива — повторная упаковка уже имеющихся блоковых классов.

Полный компактный перечень классов, хешей и изменённых методов: [offline-patch-inventory.json](offline-patch-inventory.json). Скрипт [audit_2019_offline_patch.py](../scripts/audit_2019_offline_patch.py) читает байткод без загрузки игровых классов. При сравнении инструкций учитываются значения ссылок constant pool, bootstrap-цели лямбд и exception handlers. Одинаковые сырые Code bytes сами по себе не считаются доказательством одинаковых инструкций. Аннотации, debug tables, stack maps и прочие непрозрачные атрибуты не сравниваются семантически.

[Первичная карта запросов](offline-request-map.md) отдельно показывает 17 веток handler, backend-обёртку и десять семейств отправителей, которые нужно проследить дальше.

Воспроизводимый запуск:

```powershell
python scripts/audit_2019_offline_patch.py --classes-dir 'E:\path\to\package\classes' --output 'E:\analysis\offline-patch-inventory.json'
python scripts/test_2019_patch_audit.py
```

Входные хеши закреплены в скрипте и [описании пакета](input-identity.md). Выход должен быть новым файлом вне оригинального пакета.

## Что уже исправлено нашим проектом

Наш слой остаётся отдельным от общественного патча: новые `Local*` классы и статические преобразования в [BuildBytecodeOverlay.java](../src/BuildBytecodeOverlay.java). Полного авторского Java-файла `ServerPacketHandler.java` в `src/` нет: его поставляемый class преобразуется при сборке.

- Сохранившийся обычный TCP/FML путь подключён к отдельному серверу; восстановлены необходимые registries/controllers и серверная инициализация.
- Remote адрес больше не объявляется строкой `memory`; клиентские offline tick действия ограничены integrated world.
- Backend envelope unwrap сохраняет отправителя; неподдержанные запросы учитываются, а не симулируются.
- Автоматическая перезарядка `-1 → 0`, серверный пересчёт equipment без камеры/HUD и удаление неправильной shoot-request рассылки проверены в указанном объёме.
- Обычный remote chat и жизненный цикл GO исправлены; сохранность объектов и части scoreboard данных имеет испытания.

Это **не** исправляет права команд, OP/creative смешение, режим огня, снаряды, полную инвентарную авторизацию, NPC/квестовые услуги или исторический backend. Неизвестные scoreboard поля сохранены для хранения, но их runtime-семантика не реализована. Подробные границы: [validation.md](validation.md).

## Порядок дальнейшей работы

1. Убрать безусловные права команд и creative-as-OP; установить единую модель прав конкретного игрока. Проверить обычного игрока, администратора и неизвестное имя.
2. Составить карту клиентских запросов и серверных ответов, отделяя запросы от клиентских notifications и пакетов других транспортов. Для каждого игрового действия определить, какая логика/данные уже есть.
3. Закончить бой и инвентарь: настоящие действия двух игроков, отрицательные случаи, единственность списаний и сохранение после перезапуска.
4. Проверить карту/реестры/GO/спавн, затем NPC, торговлю, задания, ПДА и переходы. Отсутствующие сервисы реализовывать по конкретным сценариям, сохраняя различие между восстановленным кодом и новой реализацией.
5. Провести тест на двух физических компьютерах и длительную сессию. Передавать сообществу воспроизводимые инструменты, настройку, правила сохранения и проверенный перечень функций/ограничений.

Этот реестр завершает первичный учёт файла патча. Он не является полной спецификацией всех исторических механик или оценкой срока восстановления. Привязка игровых данных к квестам/NPC, вся карта и успешность отдельных запросов требуют следующих отдельных проверок.

## Проверка достоверности

Скрипт повторно воспроизвёл полный inventory; независимое сравнение всех 157 Carpenter payloads подтвердило совпадения. Все 6 504 базовых и 166 patch Java-файлов сверены с сохранёнными CFR SHA-256 manifests: изменений нет. Восемь независимых classfile fixtures проверяют изменение CP при одинаковых Code bytes, ширину ldc/смещение ветвления, exception handlers, native → stub и отказы при обрезанных инструкциях/неверных границах. Исходные три JAR по-прежнему имеют закреплённые хеши. Статические fingerprints не заменяют Java verifier, игровое испытание или доказательство исторической идентичности.
